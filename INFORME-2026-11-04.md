## 1. Síntoma "HDD desconectado" — causa: el disco está conectado pero NO montado

Verificado:
- `lsblk`: `sdb1` (931 GB, NTFS, label "Seagate Expansion Drive") presente en el sistema → el disco físico SÍ está conectado.
- `/proc/mounts`: ninguna entrada para sdb1 → **no está montado**.
- `/media/<usuario>/Seagate Expansion Drive/` existe pero está vacío y es un stub `root:root` creado el 2026-11-03 23:38 (residuo del intento de automount de udisks).
- `/api/music/library/count` → `{"total":14860,"hdd_present":false}`. El detector (`os.listdir` no vacío en `api/main.py:128`) funciona bien: ve un directorio vacío y dice "ausente". El mensaje de la UI es técnicamente correcto pero engañoso: el problema es de **montaje**, no de conexión.

Contexto histórico (log del watchdog): el 03-11 23:38 se detectó el HDD y se indexó 0 canciones — el clásico trap de udisks (stub → monta como `...Drive1` o no monta). A las 00:47 registró "HDD ausente". El `udisksctl mount` por ssh falla (polkit sin tty), y nada en el sistema monta este disco automáticamente de forma fiable.

**Arreglo recomendado (definitivo)**: entrada en `/etc/fstab` con el nombre EXACTO de ruta y `nofail`:
```bash
UUID=<blkid sdb1>  /media/<usuario>/'Seagate Expansion Drive'  ntfs3  rw,nosuid,nodev,relatime,uid=1000,gid=1000,iocharset=utf8,nofail  0  0
```
Montaje inmediato: `sudo mount -t ntfs3 -o rw,nosuid,nodev,relatime,uid=1000,gid=1000,iocharset=utf8 /dev/sdb1 "/media/<usuario>/Seagate Expansion Drive"`. Después: limpiar cola fantasma de MPD y dejar que el watchdog reindexe (o `mpc update` carpeta a carpeta).

Mejora UI sugerida: distinguir "conectado pero no montado" (comparar `lsblk`/mountpoint en `/api/music/library/count`) — con el stub vacío el usuario no puede saber que falta solo el `mount`.

## 2. Síntoma "sin mensaje de reproducción en la UI" — causa: WebSocket muerto

Confirmado con handshake raw:
```
GET /ws/status (Upgrade: websocket) → HTTP 404 {"detail":"Not Found"}
```
El venv de la API (`api/venv`) tiene `uvicorn 0.46.0` **sin ninguna implementación de WebSocket** (`websockets`, `wsproto`, ni `websockets-sansio` instalados; `requirements.txt` tampoco los lista). Uvicorn sin implementación WS no procesa el upgrade: el GET cae en FastAPI, que no tiene ruta GET para `/ws/status` → 404. Consecuencia en cadena:
- `usePlayerStatus.js` nunca abre el socket → el badge de la cabecera queda en "Desconectado", "Now Playing" nunca se actualiza, barra de progreso y tiempo siempre 0:00.
- El `Player.jsx` sincroniza `<audio>` con `isPlaying` leyendo del estado WS → al no llegar estado, el audio web tampoco se arranca nunca solo.
- El contador `play_count` (incrementado en el loop del WS) nunca suma.

**Arreglo**: `api/venv/bin/pip install websockets`, añadir `websockets` a `requirements.txt`, `systemctl --user restart uma-api`. Verificar con el handshake (debe responder 101).

## 3. Audio por stream: dos problemas adicionales que impedirían escuchar aunque MPD sonara

a) **`crossOrigin="anonymous"` en el `<audio>`** (`Player.jsx:72`, presente en el bundle actual `index-CdozTgWU.js`): MPD `httpd` no envía cabeceras CORS (`Access-Control-Allow-Origin`). Con el atributo puesto, el navegador exige CORS y el stream falla al cargar. No es necesario ese atributo (no hay canvas ni análisis de píxeles) — **eliminarlo**.

b) **Cola de MPD fantasma**: la cola actual tiene 1 tema del disco sin montar; MPD responde state=`stop` con `error: ...No such file or directory`. Cualquier intento de play ahora mismo da error silencioso para el usuario. Tras montar: `mpc clear`.

Notas del stream (correctas en diseño):
- `mpd_local.conf`: httpd+lame 128k en `0.0.0.0:8010` → accesible vía Tailscale. Solo escucha **mientras MPD reproduce** (comportamiento de httpd) — por eso hoy `curl :8010` da connection refused.
- `Player.jsx` apunta a `http://<hostname>:8010/` — correcto para acceso desde cualquier dispositivo de la red Tailscale (la página se sirve por http, sin mixed content).
- Toggle "Audio Web": muta salida 0 (HDMI) y habilita 1 (stream). Indices 0-based correctos (`mpc outputs` muestra 1=HDMI, 2=stream, 3=Bluetooth; hoy HDMI está disabled y stream enabled — alguien dejó Audio Web ON).

## RONDA 4 (2026-11-04 ~13:40): arquitectura B — la web deja de depender de MPD

Análisis: MPD no estaba roto (cola 15.676 avanzando, CPU 0.5%, stream vivo), pero es
un daemon de sesión única: cola y volumen globales, stream httpd sin seek, puerto
8010 solo durante reproducción. Incompatible con multi-dispositivo Tailscale.
Decisión del usuario: **alternativa B** — cola en SQLite, reloj en el servidor, cada
navegador reproduce el archivo real vía HTTP Range; MPD queda como reproductor legado.

Implementación (bundle `index-CG1xgJXg.js`, API v0.3.0):
- `api/services/session.py`: `SessionService` — cola `radio_queue`, reloj
  `session_state` (posición = offset + now − started_at), ticker (avanza pistas al
  superar duración y salta archivos inexistentes), snapshot para WS.
- `api/models/database.py`: columnas `duration`, tablas `radio_queue`/`session_state`,
  migración mínima de duration sobre la DB vieja.
- Endpoints `/api/session/*` (snapshot, queue, play_file, add_files, shuffle_all,
  play_index, play/pause/stop/next/previous, seek) + `GET /api/music/stream?file=`
  con FileResponse (Range→206, verified) y bloqueo de traversal (400).
- Chat intents y `/ws/status` migrados de MPD a sesión.
- Player.jsx reescrito: archivo directo + seek al clicar barra + volumen local
  (localStorage) + auto-skip de archivos con error de decodificación; Library.jsx
  = cola de sesión con salto por clic; Catalog.jsx apunta a `/api/session`.
- `scripts/fill_durations.py` (ffprobe): 14.628 duraciones reales, 232 ilegibles
  (fallback 300s). Media biblioteca 276s.

Bugs encontrados y arreglados en la verificación:
- TICKER MUERTO (causa de "al acabar una canción se para o se repite"): el ticker
  hacía `os.path.exists(self.db_path)` con `DB_URL="sqlite:///../data/uma.db"` —
  una URL no es un path, siempre False, y NUNCA avanzaba pistas. Fix: quitar el
  guard. Además `play()` sobre un `<audio>` en estado `ended` REINICIA la pista
  desde 0 (el "se vuelve a reproducir"): Player ahora guarda `ended` y en el
  evento `ended` pide `/api/session/next` SOLO si el servidor aún cree que queda
  pista (position < duration-1) — así no hay doble salto con el ticker.
- MediaSession añadido (metadatos + handlers play/pause/next/prev/seekto):
  notificación Android con controles, que ayuda a Firefox Android a no suspender
  el audio en segundo plano.
- `POST /api/session/seek` → 500 `database is locked` (ticker + filler + API
  escribiendo a la vez). Fix: `make_engine()` con `PRAGMA journal_mode=WAL` +
  `busy_timeout=15000` (y timeout=30 en fill_durations.py); conversión a WAL con
  el filler parado. Seek verificado: `{"status":"ok","position":95}` http=200.
- Códec vs navegador: `.wma/.ape` imposibles en cualquier navegador → transcode
  on-the-fly ffmpeg→MP3 160k en `/api/music/stream` (verificado: WMA real →
  format=mp3). `.m4a` AAC falla SOLO en HeadlessChrome (sin códec propietario);
  Chrome/Safari/Firefox reales sí lo decodifican — mp3/flac verificados OK.
- Verificado final: shuffle_all sesión → cola 14.860 sonando; ticker avanza solo
  (cola índice 3 con play_count); seek servidor→navegador sincroniza (<1.5s);
  Range 206; traversal 400; WAL activo; API activa tras restart.
